# SaaS Website Patterns

## Purpose

Provide reusable structures for SaaS marketing sites, product pages, onboarding paths, dashboards, and pricing pages.

## Core Rule

SaaS design must sell the outcome and prove the workflow.

A SaaS site fails when it looks modern but does not explain:

- who it is for;
- what job it performs;
- how fast the user gets value;
- why the product is trustworthy;
- what plan to choose.

## SaaS Marketing Site Structure

Default structure:

1. Hero with product promise
2. Product screenshot or workflow visual
3. Use-case segments
4. Feature groups
5. Proof
6. Integrations or workflow fit
7. Security/trust where relevant
8. Pricing
9. FAQ
10. Final CTA

## Product Screenshot Pattern

Screenshots are stronger than abstract illustrations when:

- the product is new;
- workflow comprehension matters;
- trust is low;
- the user needs to imagine using it.

Good screenshot rules:

- show real interface shape;
- annotate the key value;
- avoid unreadable tiny text;
- avoid fake dashboards unless clearly illustrative.

## Feature Group Pattern

Group features by user job, not internal system modules.

Better groups:

- Capture faster
- Organize automatically
- Review with context
- Share with team

Worse groups:

- Database
- API
- Settings
- Admin

## Use-Case Pattern

Use when the product serves multiple audiences.

Each use case needs:

- audience;
- problem;
- product action;
- outcome;
- CTA or example.

## Pricing Page Pattern

A SaaS pricing page must clarify:

- plan names;
- ideal user for each plan;
- included limits;
- billing period;
- trial/refund/cancellation;
- upgrade path;
- enterprise or custom path when needed.

Pricing design should reduce anxiety, not hide tradeoffs.

## Onboarding Pattern

Good onboarding gets the user to first value quickly.

Default first-run flow:

1. choose goal;
2. connect or import minimal data;
3. generate or create first useful result;
4. show success;
5. suggest next step.

Avoid onboarding that asks for too much setup before value.

## Dashboard Pattern

A SaaS dashboard should answer:

- what is happening now;
- what needs attention;
- what can I do next;
- where do I find core objects.

Default dashboard sections:

- top-level status;
- primary action;
- recent activity;
- core object list;
- shortcuts or recommendations.

## Trust Pattern

Use trust sections when the product touches money, data, business workflows, AI output, education, legal, medical, immigration, or customer operations.

Trust can include:

- security notes;
- privacy notes;
- integration reliability;
- human review boundary;
- customer proof;
- transparent limitations.

## Final Rule

A SaaS page must make the workflow believable before it asks for payment.
